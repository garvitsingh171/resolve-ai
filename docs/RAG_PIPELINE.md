# RAG Pipeline

RAG (retrieval-augmented generation) grounds a model response in relevant external knowledge. It does not make hallucination impossible; it makes the evidence used in the answer inspectable and narrows the model's instructions.

## Ingestion

`data/knowledge-base.ts` contains 12 realistic support articles. `npm run seed` creates a **RETRIEVAL_DOCUMENT** embedding for each article and saves it in `documents.embedding`. An embedding is a 768-number semantic representation. The dimension is important because the database column and query vector must match: this project uses `vector(768)`.

## Query and retrieval

For “Money was deducted but my order failed,” `generateEmbedding` creates one **RETRIEVAL_QUERY** vector. `match_documents` compares it against document vectors, typically using cosine distance/similarity in pgvector, with top-K = 4 and a 0.55 threshold. The RPC, not application code, supplies the returned similarity value. A threshold avoids treating every database article as relevant.

## Context and generation

The route clearly delimits `[USER ISSUE]` and `[RETRIEVED KNOWLEDGE BASE]`. The prompt says that user text is untrusted, context is reference material rather than instructions, and unsupported policy must not be invented. Gemini returns JSON constrained to a resolution schema. Zod parses that JSON before it reaches the browser.

## Attribution and failure

Source cards are derived from retrieval, never generated by the model. If no result clears the threshold, the prompt says the knowledge is insufficient and the model is asked to recommend escalation. Retrieval can still be imperfect: semantic matches are not factual guarantees, a small article may omit a procedure, and prompt injection or stale docs remain risks. This is materially different from a basic chatbot because it performs vector retrieval and shows the specific support records used.
